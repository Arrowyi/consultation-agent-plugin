# Consultant task-fit routing remediation

## Purpose and scope

The consultant should assign each meaningful work unit to the agent best suited to it, not maximize subagent calls. The consultant owns intake, decomposition, interaction, verification of delegated results, final judgment, integration, and file delivery. Specialist roles own bounded tasks where their specialization can materially improve evidence, reasoning, adversarial review, source-intent audit, or prose. A simple answer or a task with no relevant specialist remains with the consultant.

This change concerns consultation-team routing, the writer's deliverable contract, dispatch result reliability, and behavioral evaluation. It does not introduce a mandatory per-tier roster, remove the consultant's direct tools, implement a new background-job service, or dynamically inject per-turn counters into the system prompt.

## Evidence and limits of the diagnosis

- The adapter registers a primary consultant, role agents, and `consultation_dispatch`; the tool forwards a consultant-selected role and prompt. The `consultation-core` team-phase and budget helpers are not called by the adapter's runtime. Mode/tier instructions in the agent and skill therefore guide behavior but do not enforce task suitability.
- The consultant and skill currently give broad standard/deep delegation instructions, while `docs/architecture.md` says standard consultations use no subagent unless a specific capability gap exists. The injected tier matrix describes caps but can be misread as a required roster.
- The writer currently supplies a blueprint, editorial review, or representative draft, not an assigned substantive chapter or section. One recorded writer dispatch returned `(no text in subagent response)`; the tool treats that placeholder as a completed tool result. Ordinary session creation and prompt failures already return explicit error strings; only the empty-success and capability preflight behavior need attention here.
- Existing session histories include both consultations with many specialist calls and consultations with direct searches and no team calls. A switched-agent author session used one writer call. Counts cannot prove why a model chose inline work, nor establish that conversation length caused the choice. Before/after evaluation must compare equivalent work units, not total dispatch counts.

## Routing contract

For each new consultation task, including a task posed after switching to consultant in an existing session:

1. Identify its mode, risk, evidence needs, deliverable, and a small set of work units. Carry over relevant user constraints, not the previous agent's execution policy or a previous consultation's role choices.
2. For **each potentially relevant role**, ask whether its specialist work could change an important claim, decision, or deliverable. Dispatch a bounded task when the answer is yes **or cannot yet be ruled out**. Skip only when there is an affirmative, task-specific reason the role's work is unnecessary. Uncertainty about a role's relevance is not a mandate to call every role: only plausible specialists enter this assessment.
3. Distinguish unknown evidence from unknown role fit. If a source is missing or stale, request evidence from explorer; if interpretation is in doubt, request analyst; if a consequential conclusion lacks a robust challenge, request critic; if source intent/independence is uncertain, request verifier; if substantive reader-facing prose is needed, request writer. Roles are not interchangeable.
4. Give each role the minimal relevant packet, expected output, and stopping boundary. Independent evidence-gathering tasks may run concurrently. Analyst follows an evidence packet; critic follows a draft conclusion or plan; writer's substantive prose follows approval of the document outline. Do not parallelize work with data dependencies.
5. The consultant checks returned material for completeness, applicability, source support, contradiction, and unsupported claims. A tool call is not proof of task completion. If a relevant role is disabled, exceeds a configured cap, fails, or returns no usable result, report the missing check and choose a justified fallback; never mark an unchecked source as clean or a missing analysis as completed.

These are **asymmetric skip rules**, not minimum role counts. Existing `tier_role_caps` and team caps remain maxima. Configuration values of zero mean that role is unavailable for the affected tier; the consultant discloses a material verification gap rather than silently calling it anyway. Cost pressure limits additional rounds, but does not justify silently omitting a first, decision-changing specialist check. Deep-tier approval remains required under the existing policy before spending the larger budget.

### Role-specific triggers and exclusions

| Role | Dispatch if relevant or uncertain | Skip only when established |
| --- | --- | --- |
| Explorer | Load-bearing facts lack current, applicable, independently sourced evidence; source coverage, provenance, or freshness is uncertain. | Suitable authoritative evidence already establishes all relevant facts, or the task requires no new evidence. |
| Analyst | Conflicting sources, causal/mechanistic reasoning, material trade-offs, or inference need an independent reading of an evidence packet. | It is a direct restatement of sufficiently established facts with no meaningful interpretive work. |
| Critic | A consequential conclusion, disputed claim, high-risk advice, or uncertain plan step could change under counter-evidence or an alternative. | There is no material conclusion to challenge, or the answer is a low-risk direct fact with no meaningful contested inference. |
| Verifier | The consultation relies on user/third-party reviews, social or forum posts, rankings, ostensibly independent evaluations, promotional material, or sources with unclear commercial relationships, coordination, or independence. The consultant need not first establish manipulation. | The key evidence has known provenance and no relevant intent/coordination or independence question remains; e.g. a straightforward authoritative specification not relying on promotional or third-party claims. |
| Writer | A durable document needs substantive reader-facing section/chapter drafts or an independent editorial pass; fit is uncertain for a substantial writing task. | Only a short immediate response or a mechanical edit is needed, with no meaningful specialist writing work. |

Verifier's remit expands from user-generated manipulation signals to **bounded provenance and influence triage** of ambiguous third-party or promotional sources. Update its prompt and output contract to distinguish observable intent signals, undisclosed sponsorship/coordination indicators, unclear independence, and missing data. A single source with no detectable signals must not be labeled `clean` solely for lack of evidence: `unknown` is appropriate when necessary account, disclosure, or comparison data are absent. Verifier does not replace explorer's factual source verification, analyst's reasoning, or critic's challenge to the conclusion. No individual piece of content is declared fake without adequate evidence.

## Author workflow and writer output

Preserve the existing intake, outline/manifest approval gate, destination approval, and proportionate technical verification. Before approval, a writer may prepare the writing blueprint; after approval, assign a specific section or chapter with audience, profile, approved map, source/evidence packet, required claims, terminology, neighboring sections, and explicit unknowns. The writer returns **usable prose**, not only headings or suggestions. It must identify unsupported facts and not manufacture citations, claim successful execution, or research beyond the supplied packet.

The consultant checks the draft's factual and cross-document consistency, obtains any needed evidence or independent review, and revises it. For file delivery the consultant writes the approved file; for inline delivery it supplies the final text. The plugin-owned writer remains read-only (`edit` and `bash` denied). A configured external `writer_delegate_agent` is not automatically covered by those permissions: its host permission policy must be checked or explicitly treated as externally controlled; the plugin must not claim it enforced read-only behavior on that agent.

## Adapter and contract boundaries

- Keep the specialist decision policy in the consultation skill as the authoritative behavioral contract; keep the consultant prompt's routing summary short and point it to the skill. Align both with `docs/architecture.md` and the five role prompts. A test checks the important cross-file invariants so conflicting role requirements do not silently reappear.
- Review `buildRuntimeBindings`: preserve stable configured model/role availability and **maximum** caps, explicitly label the tier matrix as ceilings rather than a quota or minimum. Do not add changing per-turn state to the system prompt.
- Preserve the config key `tier_role_caps` and existing role/model override behavior. Reject or explicitly report a dispatch to a disabled role instead of relying on a late session error. Do not silently change unrelated agents or tools.
- Treat absent or whitespace-only text from a completed child as an unusable dispatch result, not a successful specialist answer. Keep existing explicit errors for session/prompt failures. If a retry or configured fallback is attempted, bound it, identify the attempted model/role, and report exhaustion without pretending a result was obtained. Test the original `no text` case and a valid structured result; do not retry indefinitely or turn every blank answer into an unsupported inline conclusion.
- Keep the consultant's direct search and writing capabilities. Inline work is legitimate when appropriate; when it substitutes for an unavailable relevant specialist check, distinguish that degradation from an independently checked result.

## Evaluation and release gates

1. **Pre-register a baseline rubric.** Reconstruct representative existing user turns using the host's session and message/part records, including a consultant-switch author turn and direct-search consultations. Record the active message agent, task type, relevant role triggers and exclusions, tool calls, usable child outputs, and resulting evidence. A separate reviewer marks expected role work **before** looking at the tool decisions. Do not infer appropriateness from session length or self-reported reasoning alone.
2. **Create paired live fixtures.** Cover fast direct fact (appropriate inline), conflicting-evidence research (explorer/analyst/critic in dependency order), a straightforward authoritative specification with no promotional or third-party evidence (verifier excluded), uncertain review independence (verifier included and allowed to answer `unknown`), high-uncertainty plan step (critic), author before/after outline approval (writer blueprint then substantive draft), disabled role, empty child output, and switching to consultant late in a multi-turn conversation. Reuse the existing eval fixtures where applicable; unlike the existing checklist, record actual tool traces and grade the output.
3. **Compare against the same installed-model configuration.** Run each unambiguous fixture three times on baseline and revised installed artifacts. Require the expected specialist work in every run of an unambiguous positive case, no irrelevant specialist in every run of a negative case, and transparent handling of failure/unknown in every run. Conditional cases are reviewed with a pre-written rubric rather than forced into an all-or-none dispatch target. Record task quality, source support, latency, and tokens alongside suitability; these small trials are a release gate, not a statistical guarantee for unseen requests.
4. **Test the packaged deployment.** Run `bun test`, `bun run typecheck`, `bun run install:local`, and `CONSULTATION_PLUGIN_ENTRY=~/.local/share/consultation-agent-plugin/dist/index.js bun run integration`; then conduct the live paired runs using the installed artifact. Check whether a user-modified installed consultation skill was deliberately preserved rather than assuming new instructions replaced it. Restart OpenCode before using a rebuilt plugin.

If the paired evaluations show that clearer static routing remains insufficient, re-examine the specific failure trace before introducing further runtime intervention. A dispatch count, role quota, or mutable system-prompt reminder is **not** the default next fix.
